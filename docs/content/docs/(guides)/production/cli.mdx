The `threadsai` CLI is a thin wrapper over library calls. Both languages ship the same commands, and both read the same store format, so a store written by TypeScript can be inspected with the Python CLI and the reverse.

```text
threadsai dev [module] [--port N]           serve a host locally; prints each channel's webhook URL
threadsai start [module] [--port N]         serve a host in production
threadsai timeline <thread_id> [--branch B] print a branch's steps as JSON lines
threadsai export <branch_id>                write a branch's log (JSONL) to stdout
threadsai import <file>                     verify and store an export
threadsai repair <branch_id>                make an imported branch with a torn tail runnable
threadsai delete <thread_id> | --tenant T   delete a thread, or every thread of a tenant
threadsai gc [module] [--grace-days N]      release leftover sandboxes, remove unreferenced artifacts
threadsai eval [--agent M] [--live] ...     run saved cases: free checks, drift, a judged live run

global options: --store <dir> (default .threads), --tenant <id> (default local)
```

Packages are not published yet, so run the CLI from your clone. See [Installation](/docs/installation).

The examples below write `threadsai` for either.

## Serving: `dev` and `start`

Both load your host module, call `ready()`, and serve it.

| | TypeScript | Python |
|---|---|---|
| Default module | `threads.config.ts` | `app` (the module `app.py`) |
| What the module provides | `export default host({...})` | exactly one `host(...)` at module level, or name it: `module:attribute`, `path/to/file.py[:attribute]` |
| Server | `Bun.serve` | uvicorn (`host` extra) |
| `dev` port | `8787` | `8787`, on `127.0.0.1` |
| `start` port | `8787` | `$PORT`, else `8000`, on `0.0.0.0` |

```bash
threadsai dev
# threadsai: dev listening on http://localhost:8787
#   slack: http://localhost:8787/channels/slack/events
```

The store the host uses is the one in your module (`host({ store: sqlite(".threads") })`); `--store` applies to the other commands.

## Inspecting: `timeline`

```bash
threadsai timeline 01a0ceb2-0776-7e19-9c4c-0a3ed10d8985
threadsai timeline <thread_id> --branch <branch_id>
```

Prints one JSON object per step of the main branch (or the given one): the logged event plus whether it is a place you can fork from. See [Timeline](/docs/evals/timeline).

## Moving threads: `export`, `import`, `repair`

```bash
threadsai export <branch_id> > branch.jsonl
threadsai --store ./other-store import branch.jsonl   # prints the imported branch id
```

The export is the branch's exact log bytes, so it verifies byte-for-byte on import, in either language.

<Callout type="warn">
  An export holds the log, not the stored artifacts it points to (recorded model requests, large tool outputs). Importing into a different store fails with `artifact_missing` unless that store's `artifacts/` directory already has them, so copy the source store's `artifacts/` directory along.
</Callout>

A file cut off mid-write (a torn tail) still imports, for inspection only. `threadsai repair <branch_id>` marks it runnable again.

## Deleting: `delete`

```bash
threadsai delete <thread_id>          # one thread (of --tenant, default local)
threadsai delete --tenant acme        # every thread of a tenant
```

Deletion removes the thread's log and records that it was deleted. Threads its subagents ran are deleted with it; threads it handed off to are not. Sandboxes it still held are marked for release by the next `gc`. Deleting a team's lead deletes the whole team: its members, its team log and everything indexed for it. Everything goes in one step, or nothing does:

- `busy`: something in it is still running, has an effect whose outcome is unknown, or has a log this version can't verify. Cancel it, wait for it to stop, resolve any parked effect (or run `threadsai repair` on a torn branch), then delete.
  A log that no repair can fix (damaged in the middle, not just a torn tail) keeps its thread, and a whole-tenant delete that includes it, refused. Delete it with the version that wrote it; if that isn't possible, erasing the tenant means recreating the store without it (export the tenants you keep, then import them into a fresh store).
- `thread_in_team`: the thread is a team member or a team log. Delete its lead instead.

A refusal prints `<code>: <message>` and exits nonzero.

## Cleaning up: `gc`

```bash
threadsai gc                  # remove unreferenced artifacts older than 7 days
threadsai gc app --grace-days 1
```

With a host module, `gc` also releases sandboxes that runs left behind, using that module's sandbox providers. It never runs on its own: schedule it (for example with cron) if you want it regular.

## Evals: `eval`

```text
threadsai eval [--agent <module>] [--cases <dir>] [--case <name>]... [--live] [--store <dir>] [--strict] [--out <file>]
```

Runs every saved case under `--cases` (default `cases`). Without `--agent` it loads no user code and runs the free checks; `--agent` adds drift against your current agents; `--live` grades with a judge model. `--store` keeps the live and judge threads (by default they are not kept), `--strict` also fails on stale and skipped cases, and `--out` writes the report as JSON. Exit `0` when the run passed, `1` when it failed, `2` for a usage or config error. See [Running evals](/docs/evals/run-evals).

## Exit codes

`0` on success, `1` when the command failed (the error code and message go to stderr, for example `not_found: ...`), `2` for a usage error.

## Training data: `export --jsonl`

```bash
threadsai --store .threads --tenant local export --jsonl > turns.jsonl
threadsai --store .threads export --jsonl --thread 0192a000-0000-7000-8000-000000000001 --since 1790000000000
```

This exports one completed turn per line, including background wakes and qualifying mail turns. It also works through
`exportTrajectories(store, { threads, since })` in TypeScript and
`await export_trajectories(store, threads=..., since=...)` in Python. Both return
an expected-failure Result containing identical UTF-8 bytes for the same log.
Omit `threads` for all tenant threads; an empty list selects none. `since` includes
completions at or after that Unix millisecond timestamp. Repeat `--thread` to
select several threads. Python's global `--store` and `--tenant` go before `export`.

### Line format

Every line is canonical JSON followed by LF, with these keys:

- `format_version`: `1`
- `thread_id`, `branch_id`, `turn_id`: thread, completion branch and opening event
- `started_at`, `completed_at`: timestamps in Unix milliseconds
- `trigger`: the opening `user_input`, `woken` or `message_received` event's `type` and original `data`
- `completion`: logged turn completion reason and optional error code
- `messages`: ordered `user` and `assistant` content-part arrays, with `event_id` and `seq`;
  assistant messages also include `completeness` and `stop_reason`
- `tool_calls`: `event_id`, `seq`, and `data` with the admitted call's `call_id`, `name`,
  `input` and `request_event_id`
- `tool_results`: `event_id`, `seq`, `type` (`tool_result` or `tool_result_late`) and
  original `data`, including previews, inline content or artifact references

Renderable mail messages have role `mail` and their original `data` envelope,
including provenance. Control-only and wait-settle receipts do not render.
Wake turns retain their preceding causal late results, named in `trigger.data.causes`.

Use `seq` to merge the three arrays into execution order and `call_id` to join
calls to results. Model `tool_use` parts are proposals; `tool_calls` records admitted
calls. This is a provider-neutral format: adapt it to your fine-tuning or RL
consumer's schema before upload. It does not include full system/prior-turn
context or dereference artifacts. For portable artifact bytes, use the existing
`export <branch_id> --bundle DIR`.

All completion reasons are retained, including errors. An incomplete tail is
omitted; earlier completed turns remain exportable. Compaction model responses
are excluded. Forks do not duplicate ancestor completions. Records are ordered by
thread id, branch id, then completion sequence, independent of clocks. Missing or
foreign thread IDs return the same `not_found` error. Corrupt or unverified logs
fail the whole export without partial output.

The exporter never resolves `secret()` or reads credentials. Stored logs already
exclude resolved secrets; a registered secret encountered in output is refused.
As with any training dataset, review ordinary user/tool content before sharing it.

The complete schema is `spec/schema/trajectory.v1.schema.json` and byte semantics
are in `spec/trajectories.md`. Runnable local-store examples are
`typescript/examples/export-trajectories.ts` and `python/examples/export_trajectories.py`.
